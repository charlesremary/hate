hate — Help & Documentation

hate is a lightweight ticketing and project-management tool. Each project is a folder of plain JSON files kept under version control, so the whole team works from the same source of truth by pushing and pulling.

Why hate exists

hate is the working implementation of an argument made in a series on project management at charlesemary.com. The series isn't about this tool — it's about why conventional project management is broken, and what to do instead. hate is the "do instead."

The diagnosis:

  • Two systems that never sync. PMs live in a scheduling tool; the people doing the work live in a ticketing system. They diverge immediately and neither is authoritative, so the PM burns time reconciling them.
  • The PM as nag, not coordinator. Most tooling optimizes for chasing updates and compiling status by hand, instead of the valuable human work: unblocking dependencies and coordinating people.
  • Silent slip. Dates move with no required reason and no audit trail — a project ends up months late with no record of how. "Death by a thousand cuts, with no record of the cuts."
  • Proprietary lock-in. Ticket data sits in a SaaS database: not diffable, not version-controlled, not natively readable by the LLMs now doing much of the work.

The inversion hate is built around:

  • Tickets are the source of truth. Project status is computed from the work items, not maintained by hand in a parallel schedule. Status emerges from data, not meetings.
  • One system, git-native. Each project is a folder of plain JSON tickets under Git — history, diffing, branching, and an immutable audit trail come for free; JSON keeps everything transparent and LLM-readable.
  • Accountability on the work. The people doing the work keep their tickets current; the system surfaces slip automatically as signal; the PM's job narrows to coordination and unblocking.
  • Low cognitive overhead. You Promote a ticket instead of picking a state from a dropdown, and record only predecessors — successors are derived.
  • LLM-native by design. Because tickets are git-tracked JSON, an AI agent can create tickets for a plan and promote them as it executes — closing the gap where an LLM changes 200 files and leaves no record of what it did or why.

1. How it's organized

A project is a directory containing a .tkt/config.json file. Inside it, every ticket is its own JSON file under tickets/, and an index.json keeps a fast summary of them all.

  • + New Project creates a fresh project folder inside your projects root.
  • Open Existing… registers a project that already exists on disk — e.g. a repository a teammate cloned. Point it at the folder that contains the .tkt directory.
  • Projects in the sidebar are grouped by client.

Each project has three tabs: Tickets (the work), PM Dashboard (the schedule & health view), and Billing (logged time). The Billing tab is hidden by default — turn it on under the gear ⚙ Settings.

Renaming a project

Open the project, click the gear ⚙, and edit Project info → Display name. Only the display name changes — the folder on disk, the project's short ID (used in snapshot filenames), the ticket prefix, and existing ticket IDs are all left alone. The rename is committed to the project's git history. Older snapshots and the baseline keep the original name baked in as a historical record — they are not rewritten.

2. Tickets

Create a ticket with + New Ticket. Click any row to open its detail panel, where every field is editable inline and the full activity history is shown.

Ticket types

A ticket's type determines the workflow it follows — see §3.

TypeUse it for
taskA general unit of work — a short path, no dev/QA cycle.
dev taskWork that goes through a development and QA cycle.
design taskDesign work that goes through a review and approval cycle.
meetingA meeting that already happened. Has an attendees field. Auto-completes on creation.
administrationOverhead / non-project work. Auto-completes on creation.

Meeting and administration tickets are created already Complete — they record something that's done. You can log hours on them right in the create dialog, and they have no promote/demote workflow.

Fields

  • Priority — critical, high, medium, low.
  • Effort — xs, s, m, l, xl. This is a t-shirt size; the PM engine converts it to planned days (see §6).
  • Phase — a free-text grouping (e.g. "Discovery", "Sprint 1"). Used to filter the ticket list.
  • Assignee / Creator — people from the project's Team list.
  • Planned start & Due date — feed the schedule.
  • Predecessors — dependency links (see §5).

Attachments

Every ticket has an Attachments section in its detail panel. Drop a file onto the dashed zone, or click to pick one. Useful for things like CLAUDE.md AI-context files, design screenshots, mockups, or PDFs.

  • Files are stored in the project repo under attachments/<ticket-id>/ and are committed to git like tickets — they sync to teammates via the same push/pull.
  • Each file is capped at 25 MB. Filenames are sanitized on upload (no paths, no dotdots).
  • Images, text/markdown, and PDFs render inline in the browser; other types download. There's a small thumbnail next to image attachments in the list.
  • A closed project is read-only: you can still view and download attachments, but uploads and deletes are blocked until you reopen it.

Cross-referencing tickets

Mention another ticket's ID anywhere it makes sense — in the description, a comment, a force-close reason — and it automatically becomes a clickable chip. Pattern is <project-prefix>-<suffix>, e.g. CW-7k3x. Only references to tickets in the current project linkify; IDs with a different prefix stay as plain text.

  • Hover a chip to peek at the referenced ticket: its title, status, assignee, last activity, and a list of its attachments. Attachments in the card are themselves links — click one to view or download directly without navigating.
  • Click the chip (or the "Open ticket →" link in the card) to open the referenced ticket in the main panel.
  • Chips for tickets that don't exist render struck-through so broken references are visible at a glance.

3. The promotion model

Each workflow ticket type — task, dev task, and design task — has its own path through the statuses. Instead of picking a status directly, you promote (▲, move forward) or demote (▼, move back) from the ticket panel, and the buttons follow that type's path. Every transition is recorded in the activity log. (Meeting and administration tickets auto-complete on creation and have no workflow.)

Task

Not Started → In Progress → Complete → Closed

Dev task

Not Started → In Progress → Dev Complete → QA Testing → Complete → Closed

Dev tasks have a rework loop: demoting from QA Testing drops the ticket to Rework, and promoting from Rework sends it back to QA Testing.

Design task

Not Started → In Progress → Submitted for Review → Approved → Closed

Blocked — any workflow type

The ⛔ Block button in the ticket panel moves a ticket to Blocked — no workflow has a path into Blocked, so the button is the only way in. Promoting or demoting from Blocked returns the ticket to whatever status it was in before, which the tool figures out by reading the activity log.

Force close — skipping the workflow

Use ⏩ Force close in the ticket panel when a ticket won't be worked to completion — duplicates, scoped-out items, mistakes, anything that should leave the active list without going through promotion. It lands the ticket directly at Closed, regardless of where it was in the workflow.

Force close requires a written reason (minimum five characters), which is recorded permanently:

  • As a force_closed entry in the ticket's activity log.
  • On the ticket itself in the cancellation_reason field, shown as a banner in the panel so future readers can see why it was dropped.

This is different from normal completion — a ticket reaching Closed via promotion represents real finished work; a ticket reaching Closed via Force close represents work that was cancelled. Both are terminal: a force-closed ticket cannot be promoted, demoted, or force-closed again.

Use Force close instead of trying to delete a ticket. Deletion would corrupt the baseline; Force close transitions the ticket cleanly and preserves the audit trail. Time entries and predecessor links on a force-closed ticket are kept intact.

Automatic side effects

  • The first time a ticket reaches In Progress, its actual start date is stamped with today's date.
  • Reaching Complete or Closed stamps the closed-at timestamp. Demoting back out of those clears it again.
  • Closed is terminal for every type — a closed ticket cannot be promoted or demoted.

Logging time to promote

You can't promote a ticket out of a work status (In Progress, QA testing, or rework) without a time entry — with a description — logged since it entered that status. Promote with nothing logged and hate pops the log-time box for you, then finishes the promotion once you've saved it. Starting work and the final close don't require it, and Force close bypasses it entirely. This is always on: it's what keeps the COSMIC calibration (§7) honest — the hours behind every rate are guaranteed to be there, and every phase transition records what was actually done.

4. Logging time & billing

Open a ticket and click ⏱ Log Time. Enter a date, hours, and a short description. Hours are rounded to the nearest quarter (0.25).

  • The author of a time entry is whoever you're currently working as — the project's git identity (see §7). Set that correctly before logging time, or entries get attributed to the wrong person.
  • Meeting and administration tickets can capture hours at creation time.

The Billing tab rolls every time entry across the project into one table. Narrow it with the Start / End date range and the Author filter — the Total updates to match — then Export CSV to download exactly what's shown. Enable the tab under ⚙ Settings → "Show Billing tab".

5. Predecessors

A predecessor is a ticket that must finish before another can meaningfully start — a dependency link. Add them when creating a ticket or from the ticket panel; the predecessor has to already exist.

Predecessors are what turn a flat list of tickets into a schedule. The PM engine uses them to order work, compute the critical path, and project end dates (see §6).

6. For Project Managers

Baselining

A baseline is a frozen copy of the plan — every task's planned start, planned end, planned days, and dependencies — captured at one moment. It's the yardstick everything else is measured against. The baseline is immutable: once created, it cannot be changed or re-created.

Open the PM Dashboard tab. Before a baseline exists you'll see a pre-baseline view with a Baseline Now button — it freezes the current tickets as the plan. When baselining this way:

  • Planned days come from each ticket's effort size, via the effort_to_days map in the project config — by default xs = 1, s = 2, m = 3, l = 5, xl = 8 days. You can change these values per project under ⚙ Settings → Effort sizing. The baseline is frozen at the values in effect when you baseline — editing the map afterwards only affects new tickets and unbaselined work.
  • If a ticket has a due date, that becomes its planned end and planned days is recalculated from the date range.
  • Planned start comes from the ticket's actual or planned start date, falling back to today.

⚠ Before you baseline — read this.

The baseline is built from two inputs: each ticket's planned start date and its effort size. The baseline is immutable — once frozen, every later snapshot is measured against it, and there is no way to correct a bad baseline. If the inputs are wrong, every snapshot from then on will show slip that isn't really slip.

Start dates matter as much as effort. Two tickets with the same XL size land in very different places on the schedule depending on when each one starts. Walk the ticket list before clicking Baseline Now and ask: is this start date realistic? Does it account for predecessor work, the assignee's availability, and the project's actual kickoff?

Effort sizes are days of effort, not wall-clock time. An L = 5 means roughly five working days of focused work on that ticket — not five calendar days from start to finish. A consultant who's only on this project two days a week, a developer who's split across two projects, or anyone who starts later than planned will all show up as slipping even if their actual effort matches the estimate. If you know up front that an assignee is part-time or shared, reflect that in the start dates (push them out) or in the effort size (round up) before baselining — not after.

Capacity & the schedule check

Each team member has a Daily hours value (default 8) editable in 👤 Team. This is the per-day capacity used by the ✓ Check schedule button in the project header. The check is a one-shot analysis — it does not auto-reschedule.

For each non-terminal ticket with a planned start, due date, assignee, and effort, the check converts effort to person-hours (1 size = 8h, e.g. m = 24h), divides those hours evenly across the business days from start to due, and sums the daily load per assignee. Any day where assigned hours exceed that person's daily capacity is reported with the contributing tickets — click any chip in the report to jump to that ticket and push its dates out.

Tickets that are missing a date, assignee, or effort are listed as skipped at the bottom of the report so the check doesn't pretend to be exhaustive.

Auto-balance — get a realistic baseline schedule

The ⚖ Balance button in the project header rewrites planned-start and due dates on every open ticket so the schedule actually fits the team's daily capacity. It's a math button, not magic — it answers "how long would this take if everyone worked one realistic day at a time?"

  • Walks the predecessor graph. A ticket can't start until its predecessors finish. If a cycle exists, Balance refuses and reports the offending tickets.
  • Within a "ready" batch (no unfinished predecessors), tickets are ordered priority desc → effort desc → ID. Critical-and-large gets scheduled first.
  • Equal-split capacity. A person with three ready tickets gets each one a third of their daily hours. As tickets finish, freed capacity flows to the remaining ready set.
  • Skips closed/complete tickets — historical work isn't moved. Tickets missing an effort size or assignee are also skipped and listed in the report.
  • Preview first. Click ⚖ Balance to see the proposed changes, including the original vs proposed project end date. Click Apply to write the new dates and commit them as a single balance project (N tickets rescheduled) commit. If you hate it, one git revert away.

Baseline interaction: if the project is baselined, Balance still works — but every future snapshot will see massive slip relative to the original baseline, because the new dates intentionally don't match it. That's accurate, not a bug: Balance is showing you what the schedule should have been. Treat the first run on a baselined project as a wake-up call rather than a daily tool.

Closing a project

When a project is finished — or paused indefinitely — open Manage Tracked… in the sidebar and click Close. A closed project is read-only: you cannot add, edit, promote, demote, block, comment on, log time on, or delete tickets, and you cannot change a ticket's predecessors. Everything stays viewable — open tickets, the dashboard, the baseline, past snapshots — just not editable.

Closed projects are hidden from the sidebar by default. Toggle Show closed projects above the sidebar list to see them, or open them from the Manage modal. Closing is reversible — the same modal has a Reopen button that lifts the lock and restores write access.

Snapshots

A snapshot compares today's ticket state against the baseline. Run one with the ⟳ Snapshot button in the project header (or let the Scheduler run them automatically — see below). Each snapshot is saved by date under .tkt/pm/snapshots/. A snapshot computes:

  • Slip days — for each task, how far its current due date is past its baseline planned end.
  • Slip events — see below.
  • Projected end dates — recalculated from actual velocity.
  • Critical path and health.

Health

Every snapshot computes a project health color from total slip (as a percentage of planned duration) and the number of unresolved slip events:

HealthWhen
● GreenSlip under 10% of planned duration and no unresolved slip events.
● YellowSlip between 10% and 25%, or there is at least one unresolved slip event.
● RedSlip over 25%, or more than three unresolved slip events.

Slip events

When a snapshot finds a task whose due date has moved past its baseline — and that slippage isn't already explained — it opens a slip event with status unresolved. There's at most one open event per task at a time.

A PM resolves a slip event by attaching a reason category and a short narrative. Once resolved, that slippage is considered "explained" and won't be re-flagged. The reason categories are: estimation_error, external_dependency, scope_change, resource_diversion, technical_blocker, environment_tooling, client_delay, requirements_change.

Where to resolve them. Open the PM Dashboard tab and find the slip ledger — every unresolved event has a Resolve button. Pick a category, write the explanation, and submit.

Resolving doesn't refresh the dashboard on its own. The resolution is written to the slip ledger immediately, but the dashboard's health color and unresolved-event count are read from the latest snapshot — so they won't change until a new snapshot is run. After you resolve an event, a prompt asks whether to Run Snapshot Now or Wait. Run it now to see the effect immediately; choose Wait if you're working through several events and would rather snapshot once at the end.

How the schedule is calculated

Planned schedule (WBS from a template). Tasks are ordered by their sequence number. A task starts the business day after the latest of its dependencies ends — or on the project start date if it has none. Its duration is the template's baseline days adjusted by any duration multiplier, and the end date is reached by counting business days only (weekends are skipped).

Projected end dates (in a snapshot). The engine measures velocity — the planned days of completed work divided by the actual calendar days elapsed since the project started (clamped between 0.25× and 10×). Each unfinished task's planned duration is divided by that velocity, the task is scheduled after its predecessors' projected ends, and business days are added. Completed tasks use their actual end date. The project's projected end is the latest of them all.

Critical path. Using baseline durations and the dependency graph, the engine runs the standard forward pass (earliest start/finish) and backward pass (latest start/finish). A task's float is how long it could slip without delaying the project; tasks with zero float are on the critical path.

Scheduler

Under ⚙ Settings you can enable automatic snapshots on an interval (in hours), so health and projections stay current without anyone clicking ⟳ Snapshot. Run Now triggers a snapshot run for all projects immediately.

7. Sizing & estimating (COSMIC)

hate can size features in COSMIC function points (CFP) and use them, together with the hours you log, to measure how long work actually takes — and then to estimate a new project before you've built it. It all lives on the experimental COSMIC tab (enable it under ⚙ Settings → Show COSMIC tab).

What a function point is

A COSMIC function point measures functional size — the data movements a piece of functionality makes across a boundary, counted as Entry, Exit, Read, and Write. It is deliberately not a measure of effort, lines of code, or compute — just size. A small read operation (a command in, a lookup, a response out) is about 3 CFP whatever language it's written in.

The rule that keeps counts honest — "is your code in the loop?":

  • A human clicks a console, or a managed service does the work → your code isn't in the loop → 0 CFP. (Clicking "Create knowledge base" in a cloud console is real effort but zero functional size — track it as hours, not CFP.)
  • Your code triggers it programmatically → a few CFP for the command and its response — never for the compute the service runs.

How you tag it

Model a feature as a parent ticket that carries the size, with child tickets doing the work and logging the hours:

  • The parent gets cfp:<N> — the feature's size. Size lives on the parent only; never copy it to a child, or it double-counts. Don't log hours on the parent.
  • Each child gets parent:<parent-id> and exactly one class tag, and is where hours are logged:
    • functional — the code (the part CFP measures).
    • config — console / manual / platform setup, including IaC (0 CFP).
    • nonfunc — deploy, run, validate, troubleshoot, hardening (0 CFP).

The one line to remember: functional = code, config + nonfunc = wrap (the variable work around the code).

Simple example — a lookup_caller feature.

The op takes an identifier in (Entry), reads the caller record from the store (Read), and returns it (Exit) → 3 CFP.

PROJ-100  "lookup_caller"           tags: cfp:3          ← parent (size only)
  PROJ-101  "handler + DynamoDB read" tags: parent:PROJ-100, functional   (log hours here)
  PROJ-102  "provision the table"     tags: parent:PROJ-100, config       (0 CFP, hours)

Functional pace = PROJ-101's hours ÷ 3 CFP. The table provisioning is wrap, not size.

The COSMIC panel

The COSMIC tab rolls this up. Per feature it shows CFP, Func h (code hours), Wrap h (config + nonfunc), the h/CFP rate, and Wrap %. The card at the top is the project aggregate — the numbers you actually calibrate from:

  • h/CFP = Σ functional hours ÷ Σ CFP — your measured code rate.
  • Wrap % = (config + nonfunc) ÷ functional — the variable work around the code, as a share of it.

These emerge from the hours you log as work happens, so they get more trustworthy the more you deliver. Data-quality flags call out hours on unclassed children or logged on a parent, which would skew the rate. Because promotion now requires logged time (see §3), the hours behind these numbers can't quietly go missing.

The estimate block — bidding a new project

On a new project you have no actuals yet, but once its features are tagged with cfp: you know the total size. The Initial estimate block on the COSMIC tab turns that into an hours estimate: enter an h/CFP and a wrap % borrowed from a comparable delivered project (read them off that project's COSMIC card), and it projects:

code hours = total CFP × h/CFP
wrap hours = code hours × wrap %
total      = code + wrap

It shows the projected total next to actual hours logged so far, so as the project runs you watch the estimate and reality converge. The two inputs are saved on the project, so it's a recorded estimate — your initial bid — not a throwaway calculation. That's the loop: measure a delivered project, borrow its rates, and bid the next one on evidence instead of gut.

8. Team & Identity

The 👤 Team button in the project header opens one dialog with two distinct parts. They're related, so it helps to keep the difference straight:

You on this project

This is your identity — the name and email your Git commits and your logged time entries are attributed to. It's set per-project, which keeps work on one client's project from being attributed to another. Edit it and click Save identity; the project header's "Working as" banner reflects it.

Below the fields, a status line tells you whether that identity is linked to a team member:

  • ✓ Linked — your identity matches a member on the roster (by email or git username), so tickets can be assigned to you and your time entries resolve to a real person.
  • ⚠ Not on the roster — your identity is set but doesn't match any team member. Click Add me to the team to fix it in one step.
  • ⚠ No identity set — until you save one, commits and time entries aren't attributed to anyone.

Team members

The roster of people who can be assigned tickets on this project. Each member has a name, email, optional git username, and role. The member that matches your saved identity is tagged you.

  • + Add member reveals the add form.
  • ✎ Edit on any row lets you fix a name, email, git username, or role in place — no need to delete and re-add.
  • ✕ Remove takes a member off the roster.

Sync

Each project is a Git repository, and HATE auto-commits after every change (new ticket, status change, logged time, and so on). ⇅ Sync pulls teammates' changes (rebasing) and pushes yours; on a conflict it aborts cleanly and leaves your repo untouched. The button only appears when the project has a remote configured.
