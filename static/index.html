    Why hate exists

    hate is the working implementation of an argument made in a series on project management at charlesemary.com. The series isn't about this tool — it's about why conventional project management is broken, and what to do instead. hate is the "do instead."

    The diagnosis:

    • Two systems that never sync. PMs live in a scheduling tool; the people doing the work live in a ticketing system. They diverge immediately and neither is authoritative, so the PM burns time reconciling them.
    • The PM as nag, not coordinator. Most tooling optimizes for chasing updates and compiling status by hand, instead of the valuable human work: unblocking dependencies and coordinating people.
    • Silent slip. Dates move with no required reason and no audit trail — a project ends up months late with no record of how. "Death by a thousand cuts, with no record of the cuts."
    • Proprietary lock-in. Ticket data sits in a SaaS database: not diffable, not version-controlled, not natively readable by the LLMs now doing much of the work.

    The inversion hate is built around:

    • Tickets are the source of truth. Project status is computed from the work items, not maintained by hand in a parallel schedule. Status emerges from data, not meetings.
    • One system, git-native. Each project is a folder of plain JSON tickets under Git — history, diffing, branching, and an immutable audit trail come for free; JSON keeps everything transparent and LLM-readable.
    • Accountability on the work. The people doing the work keep their tickets current; the system surfaces slip automatically as signal; the PM's job narrows to coordination and unblocking.
    • Low cognitive overhead. You Promote a ticket instead of picking a state from a dropdown, and record only predecessors — successors are derived.
    • LLM-native by design. Because tickets are git-tracked JSON, an AI agent can create tickets for a plan and promote them as it executes — closing the gap where an LLM changes 200 files and leaves no record of what it did or why.

    1. How it's organized

    A project is a directory containing a .tkt/config.json file. Inside it, every ticket is its own JSON file under tickets/, and an index.json keeps a fast summary of them all.

    • + New Project creates a fresh project folder inside your projects root.
    • Open Existing… registers a project that already exists on disk — e.g. a repository a teammate cloned. Point it at the folder that contains the .tkt directory.
    • Add from GitHub… downloads a shared project you've been given access to: pick it from the list (hate projects are marked) or paste its GitHub address. It goes into your projects folder (an existing folder is never overwritten) and opens. Needs a Git account in Settings.
    • Projects in the sidebar are grouped by client.

    Each project has three tabs: Tickets (the work), PM Dashboard (the schedule & health view), and Billing (logged time). The Billing tab is hidden by default — turn it on under the gear ⚙ Settings.

    Renaming a project

    Open the project, click the gear ⚙, and edit Project info → Display name. Only the display name changes — the folder on disk, the project's short ID (used in snapshot filenames), the ticket prefix, and existing ticket IDs are all left alone. The rename is committed to the project's git history. Older snapshots and the baseline keep the original name baked in as a historical record — they are not rewritten.

    2. Tickets

    Create a ticket with + New Ticket. Click any row to open its detail panel, where every field is editable inline and the full activity history is shown.

    Ticket types

    A ticket's type determines the workflow it follows — see §3.

    TypeUse it for
    taskA general unit of work — a short path, no dev/QA cycle.
    dev taskWork that goes through a development and QA cycle.
    design taskDesign work that goes through a review and approval cycle.
    meetingA meeting that already happened. Has an attendees field. Auto-completes on creation.
    administrationOverhead / non-project work. Auto-completes on creation.

    Meeting and administration tickets are created already Complete — they record something that's done. You can log hours on them right in the create dialog, and they have no promote/demote workflow.

    Fields

    • Priority — critical, high, medium, low.
    • Class — Code (functional), Config (config), or Non-functional (nonfunc), stored as a tag. Config and Non-functional are wrap tickets. Leave it empty for a standalone task, a meeting, or a parent feature. See §7.
    • Est. hours (estimate_hours) — the hour estimate on a wrap ticket: 0.25 or more, in quarter hours. Code tickets have none; they are sized from the parent feature's CFP. (T-shirt effort sizing is retired; an old value shows read-only as legacy.)
    • Phase — a free-text grouping (e.g. "Discovery", "Sprint 1"). Used to filter the ticket list.
    • Assignee / Creator — people from the project's Team list.
    • Planned start & Due date — feed the schedule.
    • Predecessors — dependency links (see §5).

    Attachments

    Every ticket has an Attachments section in its detail panel. Drop a file onto the dashed zone, or click to pick one. Useful for things like CLAUDE.md AI-context files, design screenshots, mockups, or PDFs.

    • Files are stored in the project repo under attachments/<ticket-id>/ and are committed to git like tickets — they sync to teammates via the same push/pull.
    • Each file is capped at 25 MB. Filenames are sanitized on upload (no paths, no dotdots).
    • Images, text/markdown, and PDFs render inline in the browser; other types download. There's a small thumbnail next to image attachments in the list.
    • A closed project is read-only: you can still view and download attachments, but uploads and deletes are blocked until you reopen it.

    Cross-referencing tickets

    Mention another ticket's ID anywhere it makes sense — in the description, a comment, a force-close reason — and it automatically becomes a clickable chip. Pattern is <project-prefix>-<suffix>, e.g. CW-7k3x. Only references to tickets in the current project linkify; IDs with a different prefix stay as plain text.

    • Hover a chip to peek at the referenced ticket: its title, status, assignee, last activity, and a list of its attachments. Attachments in the card are themselves links — click one to view or download directly without navigating.
    • Click the chip (or the "Open ticket →" link in the card) to open the referenced ticket in the main panel.
    • Chips for tickets that don't exist render struck-through so broken references are visible at a glance.

    3. The promotion model

    Each workflow ticket type — task, dev task, and design task — has its own path through the statuses. Instead of picking a status directly, you promote (▲, move forward) or demote (▼, move back) from the ticket panel, and the buttons follow that type's path. Every transition is recorded in the activity log. (Meeting and administration tickets auto-complete on creation and have no workflow.)

    Task

    Not Started → In Progress → Complete → Closed

    Dev task

    Not Started → In Progress → Dev Complete → QA Testing → Complete → Closed

    Dev tasks have a rework loop: demoting from QA Testing drops the ticket to Rework, and promoting from Rework sends it back to QA Testing.

    Design task

    Not Started → In Progress → Submitted for Review → Approved → Closed

    Blocked — any workflow type

    The ⛔ Block button in the ticket panel moves a ticket to Blocked — no workflow has a path into Blocked, so the button is the only way in. Promoting or demoting from Blocked returns the ticket to whatever status it was in before, which the tool figures out by reading the activity log.

    Force close — skipping the workflow

    Use ⏩ Force close in the ticket panel when a ticket won't be worked to completion — duplicates, scoped-out items, mistakes, anything that should leave the active list without going through promotion. It lands the ticket directly at Closed, regardless of where it was in the workflow.

    Force close requires a written reason (minimum five characters), which is recorded permanently:

    • As a force_closed entry in the ticket's activity log.
    • On the ticket itself in the cancellation_reason field, shown as a banner in the panel so future readers can see why it was dropped.

    This is different from normal completion — a ticket reaching Closed via promotion represents real finished work; a ticket reaching Closed via Force close represents work that was cancelled. Both are terminal: a force-closed ticket cannot be promoted, demoted, or force-closed again.

    Use Force close instead of trying to delete a ticket. Deletion would corrupt the baseline; Force close transitions the ticket cleanly and preserves the audit trail. Time entries and predecessor links on a force-closed ticket are kept intact.

    Automatic side effects

    • The first time a ticket reaches In Progress, its actual start date is stamped with today's date.
    • Reaching Complete or Closed stamps the closed-at timestamp. Demoting back out of those clears it again.
    • Closed is terminal for every type — a closed ticket cannot be promoted or demoted.

    Logging time to promote

    You can't promote a ticket out of a work status (In Progress, QA testing, or rework) without a time entry — with a description — logged since it entered that status. Promote with nothing logged and hate pops the log-time box for you, then finishes the promotion once you've saved it. Starting work and the final close don't require it, and Force close bypasses it entirely. This is always on: it's what keeps the COSMIC calibration (§7) honest — the hours behind every rate are guaranteed to be there, and every phase transition records what was actually done.

    4. Logging time & billing

    Open a ticket and click ⏱ Log Time. Enter a date, hours, and a short description. Hours are rounded to the nearest quarter (0.25).

    • The author of a time entry is whoever you're currently working as — the project's git identity (see §7). Set that correctly before logging time, or entries get attributed to the wrong person.
    • Meeting and administration tickets can capture hours at creation time.

    The Billing tab rolls every time entry across the project into one table. Narrow it with the Start / End date range and the Author filter — the Total updates to match — then Export CSV to download exactly what's shown. Enable the tab under ⚙ Settings → "Show Billing tab".

    Override hours. The billing table splits each entry's hours into three columns — Hours (within a wrap ticket's hour estimate), Override (hours beyond it), and Total — each summed at the bottom. The split is cumulative per ticket against its estimate_hours (Code tickets and tickets with no estimate have no allotment, so all their hours read as normal). The Override reason column shows the recorded authorization for any override hours, or ⚠ no authorization when none was captured — so a biller can pay the override hours, question them, or drop them. (Authorizations come from strict time enforcement — see §6.)

    5. Predecessors

    A predecessor is a ticket that must finish before another can meaningfully start — a dependency link. Add them when creating a ticket or from the ticket panel; the predecessor has to already exist.

    Predecessors are what turn a flat list of tickets into a schedule. The PM engine uses them to order work, compute the critical path, and project end dates (see §6).

    6. For Project Managers

    Hour budget — what you bid vs what you've burned

    Set a project's hour budget under ⚙ Settings → Hour budget. It's split into two independent pools, and every logged hour burns down whichever pool matches the ticket's type:

    • Work hours — the build budget. Burned by task, dev task, and design task hours.
    • Admin / meeting hours — the overhead budget. Burned by administration and meeting hours. Keeping it separate stops meeting overhead from quietly eating the build budget (and vice-versa).

    Either pool can be left blank. backlog-tagged and cancelled tickets are excluded — the budget tracks committed work only. The PM Dashboard shows each pool as spent / remaining / % used and flags it Over budget once logged hours pass the cap. (A project's older single max hours cap is migrated automatically into the Work pool, so nothing set previously is lost.)

    Hours-at-risk watchlist

    The dashboard carries a standing Hours at risk watchlist: every active wrap ticket whose logged hours have reached ≥ 90% of its hour estimate. It's the early-warning list of work about to blow its estimate, and shows an all-clear state when nothing is at risk. Code tickets aren't listed: code is estimated per feature, not per ticket.

    Strict time enforcement

    With strict time enforcement on (a per-project setting), a time log that would push a wrap ticket past its hour estimate is blocked unless it's explicitly authorized. Each authorized over-log is recorded and surfaced on the dashboard under Authorized overrides — time logged past allotment, so going over is a deliberate, audited decision rather than silent scope creep. (This is separate from the always-on rule in §3 that you must log time to promote out of a work status.)

    Baselining

    A baseline is a frozen copy of the plan — every task's planned start, planned end, planned days, and dependencies — captured at one moment. It's the yardstick everything else is measured against. A baseline is never edited: the only way to change it is a Re-baseline, which archives it with a reason and freezes a new one (see The Plan strip below).

    Open the PM Dashboard tab. Before a baseline exists the Plan strip at the top says No baseline and offers Baseline now — it freezes the current tickets as the plan and commits .tkt/pm/baseline.json to the project's git history. When baselining this way:

    • Planned days come from each ticket's estimated hours divided by the assignee's daily hours (8 if unknown), rounded to whole days, minimum 1. A wrap ticket uses its estimate_hours; a Code ticket gets a share of its feature's CFP × the reference h/CFP rate (§7). The baseline is frozen at the estimates in effect when you baseline — later edits only affect unbaselined work.
    • If a ticket has a due date, that becomes its planned end and planned days is recalculated from the date range.
    • Planned start comes from the ticket's actual or planned start date, falling back to today.

    ⚠ Before you baseline — read this.

    The baseline is built from two inputs: each ticket's planned start date and its estimated hours. The baseline is frozen — every later snapshot is measured against it, and the only correction is a Re-baseline, which is recorded with its reason for everyone to see. If the inputs are wrong, every snapshot until then will show slip that isn't really slip.

    Start dates matter as much as estimates. Two tickets with the same estimate land in very different places on the schedule depending on when each one starts. Walk the ticket list before clicking Baseline now and ask: is this start date realistic? Does it account for predecessor work, the assignee's availability, and the project's actual kickoff?

    Estimates are hours of work, not wall-clock time. They become days through each person's Daily hours (👤 Team). A consultant who's only on this project two days a week, a developer who's split across two projects, or anyone who starts later than planned will all show up as slipping even if their actual hours match the estimate. If you know up front that an assignee is part-time or shared, lower their daily hours or push the start dates out before baselining — not after.

    Capacity and load

    Each team member has a Daily hours value (default 8) editable in 👤 Team. That is their capacity: how many hours of this project's work they get through per business day. Only people consume capacity — agent-generated work is effectively instant; the human review / test / debug loop is the constraint. Nothing here writes dates to tickets.

    The projected Gantt is capacity-aware. Before a baseline exists, the PM Dashboard's Gantt projects the open tickets forward from today, hour by hour:

    • Each person works their ready tickets one at a time, in order: priority (critical > high > medium > low), then dependency work order, then ID. Three 4-hour tickets for one person at 8 h/day take 1.5 days, not one day in parallel.
    • Several small tickets can share a day — there is no whole-day minimum, so a chain of ten half-hour tickets finishes in about 5 hours.
    • Different people work in parallel. A predecessor owned by someone else is still finish-to-start, and an explicit planned start date is a floor.
    • Unassigned work goes to the project's only resource when there is exactly one; otherwise it shows as its own unassigned lane at 8 h/day. A project with no resources gets one lane per assignee. An assignee matches a resource by email, git user, or name.
    • Unsized tickets (no estimate) get a 0.25 h placeholder so they still appear; the Gantt header counts them. Done and backlog tickets aren't scheduled.

    The Load table on the PM Dashboard answers "is anyone overcommitted?" directly. One row per person (plus unassigned when applicable): remaining estimated hours of tickets still in build (not yet dev_complete, cancelled, or backlog), each at its estimate minus the hours already logged (tickets with only an old effort size count as unestimated), their h/day, days of work (hours ÷ h/day), and the date they're free from — when their last ticket finishes in the capacity-aware schedule. Free-from can be later than days of work alone, because it also waits on predecessors.

    Requested end. The Load table compares each person against the project's requested end (⚙ Settings → Requested dates): it adds the working days left until then and flags each person who runs past it as over by N days, plus a project-level line. Fix an overrun by moving work to someone with room, raising daily hours, cutting scope, or agreeing a new date.

    Schedule vs request

    A client asks for a project by a date; you scope the tickets and need to know — before day 1 and every day after — whether it fits, and by how much. Set the Requested start and Requested end under ⚙ Settings → Requested dates (both optional; saved to .tkt/config.json and committed; Clear removes one). With a requested end set, the Schedule vs request card sits at the top of the PM Dashboard (both before and after a baseline); without one it's a one-line hint pointing at Settings.

    • Actual start — the earliest of any ticket's first move to in progress or first logged time, with its variance against the requested start. Blank until work starts.
    • Projected finish (likely) — the capacity-aware schedule (see How the schedule is calculated) run from the later of today and the requested start.
    • Projected finish (P85) — the same schedule with code (CFP-sized) tickets at the Monte Carlo P85 rate: the reference rate × code P85 ÷ code P50 from the COSMIC tab. With no Monte Carlo result it equals the likely finish.
    • Variance in business days against the requested dates: plus means late, minus means early.
    • Needs vs has — remaining estimated hours ÷ working days left to the requested end (h/day needed) against the team's total daily hours (people with open work), and the hours to cut (or add capacity for) to fit — or the hours spare. This is a whole-team sum: predecessors and uneven loads can still make the schedule late when the hours fit.
    • Status — ON TRACK when the P85 finish is on or before the requested end; AT RISK when the likely finish is on time but P85 is late; LATE when the likely finish is after the requested end.

    Finish-date trend. Each time the dashboard computes a forecast that differs from the last one, it's saved to .tkt/pm/forecast_history.json and committed — at most one entry per day (a later change the same day replaces that day's entry). Once there are two entries the card shows a small chart: the likely and P85 finish dates over time against a dashed requested-end line. A line climbing toward or past the requested end is the early warning. Business days throughout; flat daily capacity (no holidays).

    Closing a project

    When a project is finished — or paused indefinitely — open Project List in the sidebar and click Close. A closed project is read-only: you cannot add, edit, promote, demote, block, comment on, log time on, or delete tickets, and you cannot change a ticket's predecessors. Everything stays viewable — open tickets, the dashboard, the baseline, past snapshots — just not editable.

    Closed projects are hidden from the sidebar by default. Toggle Show closed projects above the sidebar list to see them, or open them from the Manage modal. Closing is reversible — the same modal has a Reopen button that lifts the lock and restores write access.

    The Plan strip

    The top of the PM Dashboard, above Schedule vs request, is the one place for the baseline, snapshots and slips:

    • Baseline — its date, who made it, how many tickets it covers and its planned end; or No baseline with Baseline now.
    • Last snapshot — its date and how it was taken (auto, manual or re-baseline), with Take snapshot to run one now.
    • Unresolved slips — the count of open slip events; click it to jump to the slip ledger.
    • Re-baseline… — replace the baseline (below).

    Auto-snapshot. Once a project has a baseline, opening the dashboard takes that day's snapshot if there isn't one yet — at most once a day, so slips are detected without anyone remembering to click. Take snapshot refreshes it later in the day.

    The committed audit trail. The baseline, the slip events (new slips and their resolutions) and archived baselines are committed to the project's git history as they change, each commit touching only those files. Daily snapshot files are derived and change every day, so they stay out of git: .tkt/pm/.gitignore ignores snapshots/.

    Re-baseline. When the plan genuinely changes (the client moved scope, a new phase was added), click Re-baseline… and give a reason of at least 5 characters. The current baseline is archived to .tkt/pm/baselines/<date>-<n>.json with the reason, who did it and when; any unresolved slip events against it are closed as rebaseline with the reason as the explanation (they stay in the ledger); a new baseline is frozen from the current tickets; and all of it is one commit, re-baseline: <reason>. The strip counts the earlier baselines. Re-baselining resets the yardstick, so use it for real plan changes, not to make slips disappear — the reason is in the history.

    Snapshots

    A snapshot compares today's ticket state against the baseline. One is taken automatically the first time the dashboard opens each day; take another with Take snapshot in the Plan strip. Each snapshot is saved by date under .tkt/pm/snapshots/ (not committed). A snapshot computes:

    • Slip days — for each task, how far its current due date is past its baseline planned end.
    • Slip events — see below.
    • Projected end dates — recalculated from actual velocity.
    • Critical path and health.

    Health

    Every snapshot computes a project health color from total slip (as a percentage of planned duration) and the number of unresolved slip events:

    HealthWhen
    ● GreenSlip under 10% of planned duration and no unresolved slip events.
    ● YellowSlip between 10% and 25%, or there is at least one unresolved slip event.
    ● RedSlip over 25%, or more than three unresolved slip events.

    Slip events

    When a snapshot finds a task whose due date has moved past its baseline — and that slippage isn't already explained — it opens a slip event with status unresolved. There's at most one open event per task at a time.

    A PM resolves a slip event by attaching a reason category and a short narrative. Once resolved, that slippage is considered "explained" and won't be re-flagged. The reason categories are: estimation_error, external_dependency, scope_change, resource_diversion, technical_blocker, environment_tooling, client_delay, requirements_change (and rebaseline, set by a re-baseline). New slip events and every resolution are committed.

    Where to resolve them. Open the PM Dashboard tab and click the unresolved count in the Plan strip to jump to the slip ledger — every unresolved event has a Resolve button. Pick a category, write the explanation, and submit. The resolution is committed, a fresh snapshot is taken and the dashboard reloads, so health and counts reflect it straight away.

    How the schedule is calculated

    Planned schedule (WBS from a template). Tasks are ordered by their sequence number. A task starts the business day after the latest of its dependencies ends — or on the project start date if it has none. Its duration is the template's baseline days adjusted by any duration multiplier, and the end date is reached by counting business days only (weekends are skipped).

    Projected end dates (in a snapshot). The engine measures velocity — the planned days of completed work divided by the actual calendar days elapsed since the project started (clamped between 0.25× and 10×). Each unfinished task's planned duration is divided by that velocity, the task is scheduled after its predecessors' projected ends, and business days are added. Completed tasks use their actual end date. The project's projected end is the latest of them all.

    Critical path. Using baseline durations and the dependency graph, the engine runs the standard forward pass (earliest start/finish) and backward pass (latest start/finish). A task's float is how long it could slip without delaying the project; tasks with zero float are on the critical path.

    Scheduler

    Under ⚙ Settings you can enable automatic snapshots on an interval (in hours), so health and projections stay current without anyone opening the dashboard. Run Now triggers a snapshot run for all projects immediately.

    7. Sizing & estimating (COSMIC)

    hate can size features in COSMIC function points (CFP) and use them, together with the hours you log, to measure how long work actually takes — and then to estimate a new project before you've built it. It all lives on the COSMIC tab.

    What a function point is

    A COSMIC function point measures functional size — the data movements a piece of functionality makes across a boundary, counted as Entry, Exit, Read, and Write. It is deliberately not a measure of effort, lines of code, or compute — just size. A small read operation (a command in, a lookup, a response out) is about 3 CFP whatever language it's written in.

    The rule that keeps counts honest — "is your code in the loop?":

    • A human clicks a console, or a managed service does the work → your code isn't in the loop → 0 CFP. (Clicking "Create knowledge base" in a cloud console is real effort but zero functional size — track it as hours, not CFP.)
    • Your code triggers it programmatically → a few CFP for the command and its response — never for the compute the service runs.

    How you tag it

    Model a feature as a parent ticket that carries the size, with child tickets doing the work and logging the hours:

    • The parent gets cfp:<N> — the feature's size. Size lives on the parent only; never copy it to a child, or it double-counts. Don't log hours on the parent.
    • Each child gets parent:<parent-id> and exactly one class tag, and is where hours are logged:
      • Code (functional) — the human loop around generated code: prompt, review, run, debug. No hour estimate: it's sized from the parent's CFP.
      • Config (config) — console / manual / platform setup, including IaC (0 CFP). Gets an hour estimate.
      • Non-functional (nonfunc) — deploy, run, validate, troubleshoot, hardening (0 CFP). Gets an hour estimate.

    The one line to remember: Code is sized by CFP; wrap (Config + Non-functional) is sized in hours with estimate_hours (0.25, 0.5, 1, 2, 4, 8…). A wrap ticket can also carry an optional type:<name> tag. A small self-contained feature can skip the parent: one ticket with both cfp: and the Code class.

    The rules are checked at a child's first promote out of Not Started (creating and editing never block): it needs exactly one class, a wrap child needs estimate_hours, a Code child must not have one, and no child carries cfp:. The ticket list badges children that are missing a class or estimate.

    Simple example — a lookup_caller feature.

    The op takes an identifier in (Entry), reads the caller record from the store (Read), and returns it (Exit) → 3 CFP.

    PROJ-100  "lookup_caller"           tags: cfp:3          ← parent (size only)
  PROJ-101  "handler + DynamoDB read" tags: parent:PROJ-100, functional   (log hours here)
  PROJ-102  "provision the table"     tags: parent:PROJ-100, config       estimate_hours: 1

    Code pace = PROJ-101's hours ÷ 3 CFP. The table provisioning is wrap: an hour estimate, not size.

    The COSMIC panel

    Per feature the tab shows CFP, Code h, Wrap h (config + nonfunc), the h/CFP rate, and Wrap % (info only; the estimate doesn't use it). The card at the top is the project aggregate, and h/CFP = Σ Code hours ÷ Σ CFP is your measured code rate. Data-quality flags call out hours on unclassed children or logged on a parent, which would skew the rate.

    The estimate — Monte Carlo

    The Estimate panel turns this project's CFP into an hours range. Pick the reference features it learns the code rate from, in any mix:

    • Specific past projects — same domain; the normal case.
    • All past projects — a deliberately wide range for a project unlike anything before.
    • This project's finished features — once enough are done, these dominate the draw (own share = own N ÷ (own N + 5), 100% from 15).
    • Manual baseline — a typed rate range in h/CFP for a cold start (fresh install, or a first-of-its-kind project with nothing to borrow from).

    Manual baseline. Type Low / Likely / High h/CFP, read as P10 / P50 / P90: Likely is the median rate, and 1 in 10 features should come in under Low, 1 in 10 over High. Or pick a preset:

    • Agentic (Claude-assisted) — 0.08 / 0.25 / 1.00 h/CFP (the default; from past Claude-assisted projects, with High set near the worst observed rate).
    • Traditional (hand-coded) — 8 / 12 / 18 h/CFP (the industry band).
    • Custom — editing any value switches to this.

    The range is used as typed (not widened) and counts as 5 features of evidence: it shares the non-own draws with borrowed features as 5 : borrowed N, and hands over to this project's finished features as they come in — 0 done → all baseline, 5 done → half, 15+ done → the baseline no longer counts. With it ticked the 3-feature minimum doesn't apply, and while there are fewer than 3 real reference features its Likely is also the rate code tickets are scheduled at. The result note shows the mix, e.g. "Draws: 40% manual baseline, 60% own features".

    New projects with no saved estimate inputs start on the manual baseline (Agentic) + this project's finished features, so a range shows straight away; the panel says so until you change an input. Unticking everything gives "no reference selected".

    Features under the min feature size (default 3 CFP) are left out so tiny features with extreme rates don't dominate; counting uncertainty (± %) widens the range for rough CFP counts. Changing any input recalculates at once — there's no run button.

    It runs 10,000 simulations (fixed seed, so the numbers are stable): each feature's code hours = its CFP × a rate drawn from the references, with the spread widened 1.5× (calibrated by backtesting). Platform wrap is not simulated: it's logged hours on finished wrap tickets plus estimate_hours on the rest. The table shows Code wrap, Platform wrap, and Total at P50 / P85 / P95, with a histogram of the totals, the number of reference features and the own/borrowed mix, actual hours so far, and a code projected finish (actual code hours on done features + the simulated rest). It needs at least 3 reference features, or the manual baseline.

    The estimate is display only. The max-hours cap stays manual: set it under ⚙ Settings → Hour budget.

    Calibration slice — a new kind of project

    With no comparable past project: count CFP for the whole spec, estimate with All past projects (the wide range) or the Manual baseline when there are none, and add explicit discovery wrap tickets for the unknown platform. Then pick 3–5 representative features, tag their parents calibration-slice, and build them first. The tab marks them slice and shows "Calibration slice: N of M done". As they finish, tick This project's finished features and re-estimate the rest from the project's own rates. If you must bid one number up front, bid P90–P95 of the wide range, and revisit the cap after the slice.

    Converted estimates

    Older wrap tickets sized with the retired t-shirt effort and no estimate_hours get hours converted from their effort size. Those are day-based and usually far too big, so the COSMIC estimate leaves them out of the platform wrap sum, and the Tickets tab shows a banner counting them; Review filters the list to them so you can set real hour estimates.

    8. Team & Identity

    The 👤 Team button in the project header opens one dialog with two distinct parts. They're related, so it helps to keep the difference straight:

    You on this project

    This is your identity — the name and email your Git commits and your logged time entries are attributed to. It's set per-project, which keeps work on one client's project from being attributed to another. Edit it and click Save identity; the project header's "Working as" banner reflects it.

    Below the fields, a status line tells you whether that identity is linked to a team member:

    • ✓ Linked — your identity matches a member on the roster (by email or git username), so tickets can be assigned to you and your time entries resolve to a real person.
    • ⚠ Not on the roster — your identity is set but doesn't match any team member. Click Add me to the team to fix it in one step.
    • ⚠ No identity set — until you save one, commits and time entries aren't attributed to anyone.

    Team members

    The roster of people who can be assigned tickets on this project. Each member has a name, email, optional git username, and role. The member that matches your saved identity is tagged you.

    • + Add member reveals the add form.
    • ✎ Edit on any row lets you fix a name, email, git username, or role in place — no need to delete and re-add.
    • ✕ Remove takes a member off the roster.

    Sync

    Each project is a Git repository, and HATE auto-commits after every change (new ticket, status change, logged time, and so on). ⇅ Sync brings in teammates' changes and shares yours. When both sides changed the same thing, hate combines them itself: the same slip seen on two computers becomes one; a ticket edited on both keeps the newer edit and notes the other value in its activity; anything it can't combine keeps the shared version and saves yours under .tkt/conflicts/. Your project is never left half-updated. The button only appears when the project has a shared copy (a remote).

    Git account and automatic sync

    Under ⚙ Settings → Git account, paste a GitHub token and click Test connection and save. It's kept in this computer's password store (Keychain on a Mac, Credential Manager on Windows), never in a project, so it's never shared with the team. Your GitHub name and email are used for your changes. Settings warns 14 days before the token expires, with a Replace token button. If Git isn't installed, Settings shows how to install it instead.

    With an account set up, projects sync on their own: when you open one, every 5 minutes, before the PM dashboard shows (if the last update is over a minute old), and about 10 seconds after you change something. The light in the project header says how it's going:

    • Synced (green): up to date with your team, with the time of the last sync.
    • Syncing (blue): working on it.
    • Offline (grey): GitHub couldn't be reached. Your changes are saved on this computer and go out automatically when the connection is back.
    • Needs attention (red): click it for what happened in plain words, e.g. the token was rejected, or two versions of a file couldn't be combined and yours was saved aside.

    Without a Git account nothing syncs in the background; ⇅ Sync still works. The PM walkthrough is in docs/pm-guide.md.

    9. Working in Agile

    hate is deliberately methodology-agnostic. Its primitives — a parent/child hierarchy, a phase grouping, a backlog tag, per-type status workflows, and hour estimates — assume neither waterfall nor Scrum nor Kanban. The examples elsewhere in this guide read as phase-gated (Discovery → Build → QA → Deploy) because that suits agentic, near-waterfall delivery. hate is not an Agile tool — but if you run Scrum, the same primitives map onto it cleanly by convention. Here is the recommended approach.

    The mapping

    Agile conceptIn hateHow
    EpicParent ticketA large feature or theme. Carries cfp: and/or type: if you want sizing; never logs hours.
    StoryChild ticketparent:<epic-id>, one class tag (wrap stories get estimate_hours) — and where hours are logged.
    SprintphaseName phases Sprint 01, Sprint 02, … The phase rollup then reads as sprint progress (hours-weighted % complete).
    Product backlogbacklog tagAlready excluded from completion %, schedule, and capacity — i.e. "not committed to a sprint yet."
    Sprint planningRemove backlog + set phasePulling a story into a sprint is one tag removal and one phase set.
    Dev lifecycle / DoDTicket statusThe promotion workflow (§3) — Not Started → In Progress → Dev Complete → QA → Complete — is each story's mini-lifecycle inside the sprint.
    VelocityCompleted est. hours per phaseDone estimated hours per sprint, straight off the phase rollup.
    Ceremoniesmeeting / administrationPlanning, standups, review, retro — phase them into the sprint; they burn the admin/meeting hour pool (§6).

    The one idea that makes it click. You have two independent axes. status is where a ticket sits in its dev lifecycle; phase is which bucket of time it belongs to. In phase-gated waterfall you spend phase on the lifecycle stage. In Agile each story runs its own lifecycle via status, which frees up phase to mean the sprint. You are not adding a concept — you are re-assigning which axis carries the timebox.

    An epic is not a backlog

    The backlog is not a container — it's a state (the backlog tag) any story can be in, across many epics. An epic can have three stories already in Sprint 4 and five still in the backlog. So model the epic as a parent and the backlog as a tag on the children, never as the epic itself.

    PROJ-100  "Checkout revamp"     tags: cfp:24                                     ← epic (parent)
  PROJ-101  "Guest checkout"     tags: parent:PROJ-100, functional, phase:Sprint 03   ← committed story
  PROJ-102  "Saved cards"        tags: parent:PROJ-100, functional, backlog           ← still in the backlog

    Where it doesn't fit — know the edges

    hate was not built to be Scrum, so a few things are conventions rather than first-class features:

    • Two levels, not three. The hierarchy is parent → child (one level of nesting); Agile's epic → story → task is three. Pick which two get the real hierarchy. The recommended Epic = parent, Story = child logs hours at the story level. If a team must split stories into tasks and log time per task, instead make the epic a tag (e.g. epic:checkout) with the story as the parent and the task as the child.
    • Story points vs CFP. cfp: is objective COSMIC functional size, not relative story points — don't cram points into it. Velocity comes from estimated hours on the phase rollup; CFP sizes the code and drives the estimate (§7).
    • No strictly-ranked backlog. Agile backlogs are totally ordered (1…N). hate has four priority buckets, not a strict rank. If you need an ordered backlog, adopt a convention — a rank: tag, or predecessors.
    • A sprint isn't a first-class timebox. A phase is a string, not a dated container with a burndown. Infer sprint dates from ticket start/due dates, and run a snapshot (§6) at each sprint boundary to capture velocity history. A native sprint entity — fixed dates plus a burndown chart — is the one piece you would have to build for the full ceremony.

    Bottom line: set phase = sprint, tag uncommitted work backlog, let status carry each story's lifecycle, and read velocity off the phase rollup — and you are running Agile on the same primitives everything else here uses.
